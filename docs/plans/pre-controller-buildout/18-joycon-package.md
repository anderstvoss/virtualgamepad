# Brief 18: Switch 1 Joy-Con L/R package (#297)

Read [ground-rules.md](ground-rules.md), [brief 15](15-xbox-series-package.md), #297 and #322, then the Switch Pro implementation (`crates/gr-curated-controllers/src/switch_pro.rs` and `switch_pro/protocol.rs`). This is a planning brief only; do not start code until its blockers clear.

**Lane:** Controller. **Families:** Joy-Con (L) and Joy-Con (R), distinct curated handles; source registry IDs `switch-joycon-family`, `switch-joycon-left`, `switch-joycon-right`. **PR boundaries:** 18a–18e, one separate implementation PR each.
**Blocked by:** this brief on `main`, completed VG-1b (`docs/spec/input-model-state-and-mutation.md` `9 a–e), adopted source-research pin and eligible Linux host for real acceptance. Descriptor fidelity remains an explicit evidence gate, not an assumed fact.

## Goal and decided context

Implement `create_joycon_left(CreationOptions, JoyConLeftOptions)` and `create_joycon_right(CreationOptions, JoyConRightOptions)` in curated and ordinary root (C7). **Each half is its own controller**, one `linux.uhid.bluetooth` (BUS_BLUETOOTH metadata) realization per half: Nintendo 057e:2006 L and 057e:2007 R. A pair is **two independent devices**. The application, `joycond` or SDL handles any pairing/combining; virtualgamepad **never** manufactures a 057e:2008 combined device or manages consumer pairing. Bluetooth-bus UHID is local kernel HID presentation, **not radio discovery/pairing** (#164).

Out of scope for this package: Switch 2 Joy-Con, real Bluetooth HCI/BlueZ pairing, USB Charging Grip 057e:200e (separate #165 receiver/topology follow-up), a USB-bus half, game-specific button remapping and a fabricated combined controller. Right-only NFC/IR MCU remains a separately bounded optional sub-step, never aliased to mouse axes or generic gamepad buttons.

**Post-VG-1b input API, not the current interim shape:** separate `JoyConLeftInputs` and `JoyConRightInputs` with native per-half buttons, 12-bit stick and motion. `set_inputs`, family-native per-field setters and `edit_inputs` on each handle delegate to **one transactional final-state validator**, with `inputs()` as the accepted read view; neutralize affects only caller inputs. Battery, charging, identity, colours, SPI/calibration/persistent resource, protocol timers, rail state, LEDs and host outputs live in independent typed views. The brief **assumes VG-1b steps d/e have landed**. Typed refusals cover unsupported per-half operations; no generic input masks, implicit fallback or invented edge queue. Preserve `commit()` and `service()`; caller commits between important button edges.

Caller-specified identity at creation with per-instance defaults (#156, #162): each half has its own six-byte Bluetooth-device-info identity/uniq, side/type, optional serial where evidenced, colours and version metadata. Generated defaults must not collide during concurrent creation; reconnect values are stable within the promised instance lifecycle. No actual address-shaped examples, serial dumps or real pairing material belong in fixtures. Do not conflate firmware version, HID version or an address-derived SDL serial.

## Evidence and reuse boundary

Authoritative *source-only* scope: `records/controller/switch-joycon-family.json`, `switch-joycon-left.json`, `switch-joycon-right.json` in [controller-protocol-research](https://github.com/anderstvoss/controller-protocol-research), plus [L0 device ledger](https://github.com/anderstvoss/controller-protocol-research/blob/main/docs/ledgers/switch-joycon-l0.md), [MCU ledger](https://github.com/anderstvoss/controller-protocol-research/blob/main/docs/ledgers/switch-joycon-mcu-l0.md), [kernel/SDL open paths](https://github.com/anderstvoss/controller-protocol-research/blob/main/docs/switch-joycon-open-path.md), [pair-shape](https://github.com/anderstvoss/controller-protocol-research/blob/main/docs/switch-joycon-pair-shape.md), [consumer survey](https://github.com/anderstvoss/controller-protocol-research/blob/main/docs/switch-joycon-consumer-survey.md), [decision table](https://github.com/anderstvoss/controller-protocol-research/blob/main/docs/switch-joycon-decision-table.md), [permissions](https://github.com/anderstvoss/controller-protocol-research/blob/main/docs/switch-joycon-permissions.md) and [18-case validation plan](https://github.com/anderstvoss/controller-protocol-research/blob/main/docs/switch-joycon-validation-plan.md).

- **Shared with Switch Pro only where records support exact common semantics:** `swpro-l0-device-subcmd-ack-byte` (0x01 request / 0x21 reply and echo/ACK semantics), `swpro-l0-device-report30-full` (full-report envelope), `swpro-l0-device-info02-fields`, `swpro-l0-device-factory-spi-map`, `swpro-l0-device-user-spi-magic` and `swpro-l0-device-rumble-word-tables`. Reuse a small Nintendo framing/ACK/SPI/rumble primitive extracted from Switch Pro **without altering its behavior**; its current `SwitchUsbProtocol` is USB-specific and cannot be reused wholesale as a Bluetooth device.
- **Per half, never copied blindly from Pro:** `joycon-hid-nintendo-bus-binding`; L/R PID and type; controls/SL/SR; left versus right stick calibration address/order (`joycon-a-calibration-per-side`), user SPI magic and colour bytes; single-stick layout with unknown unused opposite-stick bytes; battery/connection bits; IMU axis semantics (`joycon-a-right-imu-signs`); LED differences (`joycon-a-home-led-and-rail-buttons`); nominal cadence and transport framing. The right half alone has Home LED and NFC/IR.
- **Consumer-specific init paths:** `joycon-c-kernel-bt-probe-required`, `joycon-c-sdl3-bt-open-gates`, `joycon-c-kernel-version-and-identity` and `joycon-joycond-pair-combination` / `joycon-sdl-hidapi-pair-combination`. Kernel `hid-nintendo` needs device-info 0x02, IMU enable 0x40, full input mode 0x03 and vibration enable 0x48 for successful L/R probe; SPI calibration can default. Pinned SDL3 has different fatal/default paths (factory stick SPI read matters) and SDL2 differs again. Test each, not an invented universal init path.
- **Right-only MCU, if authorized:** `joycon-b-yamakaky-mcu`, `joycon-b-eden-nfc`, `joycon-b-yamakaky-ir`, [MCU L0 ledger](https://github.com/anderstvoss/controller-protocol-research/blob/main/docs/ledgers/switch-joycon-mcu-l0.md). Report mode 0x31 and MCU state/config/reply handling are not equivalent to a functioning camera or NFC antenna.

The pinned `hid-nintendo`, SDL, `joycond` and GPL emulator/consumer repositories are **consumer evidence**, not retail device proof; cite source IDs, commits and lines, paraphrase the behavior and never copy GPL passages or raw capture content. All Joy-Con families target **source evidence first**, with physical evidence absent. Real retail Bluetooth HID descriptors, on-air names, unused opposite-stick values, some ACKs and firmware/serial formats are **No evidence**. A provisional synthetic descriptor, if used, must be clearly marked **WIP compatibility**, not physically faithful or host accepted.

## Ordered steps (separate implementation PRs, each to `main`)

**18a. Two family contracts, input-only state and metadata.** Register two separate compiled definitions and realized target restrictions. Add `JoyConLeftInputs` (D-pad, Minus, Capture, L/ZL, stick/click, SL/SR, IMU) and `JoyConRightInputs` (A/B/X/Y, Plus, Home, R/ZR, stick/click, SL/SR, IMU), independent native output/identity/calibration/rail/clock views, and per-instance colours. Build all mutation forms on completed VG-1b. **Done when:** per-half control inventory, neutral/boundaries, 12-bit conversion, identity isolation, incorrect-side refusal, no-op/dirty preservation and transactional rollback pass deterministic tests.

**18b. Shared Nintendo codec and half-specific subcommand/SPI layers.** Extract only evidenced Switch Pro common envelopes and acknowledgement/rumble helpers, keeping the existing Pro unit fixtures intact. Add independent L/R device-info, 0x3F simple and 0x30 full mode, 0x21 replies to 0x01 commands, SPI user/factory calibration and safe per-instance ephemeral defaults, battery/charging, report timers, 3 IMU samples per full report, per-side player LED and R-only Home LED. Implement source-supported 0x02/0x03/0x10/0x30/0x40/0x48 and supported output/rumble commands with exact ACK/refusal; unknown commands get explicit errors, never guessed success. **Done when:** synthetic table tests assert each declared host request/reply, framing, retries/timeouts, SPI valid/invalid/fallback, right IMU sign conversion, side isolation and absence of leaked mutable SPI state. Treat output protocol completion as distinct from physical rumble/sensor behavior.

**18c. Bluetooth-bus UHID realizations and converged root wiring.** One controller + one Linux BUS_BLUETOOTH UHID identity per half; no third paired device. Implement creation through `create_joycon_left` and `create_joycon_right` with `CreationOptions` and per-half options; protocol session, typed inputs/edit/read/metadata, output retention and precise lifecycle. Use a source-backed descriptor when available; any provisional descriptor remains WIP and must not be reported as faithful. **Done when:** fake-provider create/close/rollback and host-request tests pass; on an eligible Linux host `hid-nintendo` binds each half separately, gives expected main/IMU/LED nodes, executes the required probe, and SDL2/SDL3 HIDAPI open paths are separately observed. If descriptor or host access blocks this, document the gate and leave host cells untested; do not invent a passing result. Future PR updates API snapshots and `docs/ALPHA_API_MIGRATION.md` with all declarations/deltas.

**18d. Right-hand MCU stretch, separate gated PR.** Only after a specific Anders decision to include it: add native R-only MCU power/config/state, 0x31 report region, 0x11 requests and 0x20/0x21/0x22 management, explicitly scoped NFC tag polling/fragment transfers and IR frame fragments. No NFC credentials, real tag data, camera images or firmware material. **Done when:** fully synthetic 160x120 grayscale 64-fragment frame tests, CRC, dropped/repeated/out-of-order fragments, NFC detect/read/write state with timeouts/cancellation and clean shutdown pass; L refuses MCU operations. Stay WIP/Not supported until independent physical tests justify more. Deferring 18d does not prevent L/R gamepad acceptance.

**18e. Per-half acceptance, consumer pairing and #166 timing.** Add future `acceptance/` manifestations and support-matrix rows for each half, exact target and identity. Follow the [JC-01 to JC-18 matrix](https://github.com/anderstvoss/controller-protocol-research/blob/main/docs/switch-joycon-validation-plan.md): kernel `hid-nintendo` and standalone evdev main/IMU/LED, SDL3/SDL2 raw-vs-evdev, and `joycond` consumer-created pairing/unpairing; test one half removed mid-pair and verify **virtualgamepad has still only created two independent halves**. Record precise renderer/backends, ACLs and node identity; Steam Input stays an explicitly manual/untested consumer until exercised. Measure #166 create-to-consumer-owned first valid neutral observation and removal-to-node-gone separately for L, R, concurrent L+R, and repeated N cycles. **Done when:** every matrix cell is linked to exact candidate SHA, research pin, kernel, SDL/joycond version, command/result or marked missing. Do not invent a first-neutral oracle, physical cadence, timing budget, HD rumble actuation or NFC/IR acceptance.

## Host setup and permissions

A Linux host with `/dev/uhid` writer access, `hid-nintendo` present/bindable, permitted hidraw and evdev/IMU nodes, readable battery and LED surfaces, and a pinned SDL2/SDL3/joycond test environment is needed. The already signed-off #258 host audit defaults to existing creator permissions and distro/seat consumer ACLs, **not** blanket hidraw, group `input` membership, root daemons by default or automatic rules. Document effective `udevadm`/ACL/driver ownership and explicit permission failures. Published Steam udev grants for L/R hidraw do **not** establish Steam client functionality. Pinned `joycond` may deliberately conceal physical main evdev nodes with udev and run privileged to create a *consumer* uinput pair; test it only under owner-approved host configuration, restore rules on exit, and watch for duplicates. Future permissions changes require a new #258-style audit row and owner sign-off. No real radio or BlueZ prerequisites for `linux.uhid.bluetooth`.

## Snapshot, migration and support categories

This docs PR adds **no implementation, snapshots, `acceptance/`, submodule updates or host policy**. The later per-step PRs record explicit API deltas, update snapshots and `docs/ALPHA_API_MIGRATION.md`, and add deterministic regressions. Split native-function rows by half and by realization: L and R buttons, calibrated stick, IMU, battery/charging, report mode, SPI persistence, player LEDs, R Home LED, rumble, rail, R MCU/NFC/IR, identity and lifecycle. Use the existing support-matrix realization statuses while separately identifying **Not supported**, **WIP**, **source evidence** and **physical evidence**; currently only source-backed research is established. Non-representable native operations must fail explicitly; optional R MCU does not become a spurious generic control. Kernel/SDL/joycond acceptance is virtual-host evidence, never a retail-device capture.
