## Goal and decided context

Add `create_switch2_pro(CreationOptions, Switch2ProOptions)` to the curated crate and ordinary root (C7). This is a new family after Alpha 2, not a change to Switch Pro (#156). Preserve Nintendo spatial face semantics (south B, east A, west Y, north X), separate native GR/GL/C, Capture, Home, Plus/Minus, digital L/R/ZL/ZR, stick clicks, D-pad and two sticks. Do not map C to Capture or a grip to an existing button. The source-supported consumer inventory is not proof that every retail firmware emits those controls independently.

- **First realization — `linux.uinput`:** playable Linux evdev matching the pinned kernel-declared shape, not native USB/HIDAPI recognition. Prioritize full independent base controls plus GR/GL/C, and conventional two-magnitude FF when justified. Native IMU, HD rumble words, LED/configuration commands, USB identity and battery are not represented by this reduced surface; add no dummy capabilities. All discrepancies, including axis fuzz, identity/bus presentation, optional FF, mapping and omitted companion nodes, are explicit technical restrictions and regression cases.
- **Later native USB — USB/IP production target:** one composite USB device with a HID input/output interface and separate vendor-class bulk configuration interface. Follow brief 17: `dummy_hcd` is secondary and experimental only as needed; each path independently requires new audit amendment and sign-off. Existing `linux.usbip.usb-audio` is HID/UAC, not a generic vendor-bulk implementation; the composite provider and its compiled realization ID are new design work. Existing `linux.dummy_hcd.usb-hid` is unavailable because of the f_hid request contract, not a supported shortcut. Never silently fall back from a requested USB target to uinput.
- **Not targetable today:** `linux.uhid.usb` and `linux.uhid.bluetooth` cannot implement the required USB topology/bulk setup. No pinned HID-only working native path; future Bluetooth-bus UHID is permissible only after a separate research PR evidences a consumer path and a separate scoped implementation. Real Bluetooth discovery, pairing, reconnect and console acceptance remain #164, not inferred from local bus metadata.
- No runtime descriptor injection, generic mutable state, arbitrary controller aliases or provider-owned protocol logic. Any compatibility shim has a named creation-time toggle, explicit default and scope, and tests with it enabled/disabled. No USB/SDL identity spoof shim assumed necessary for uinput.

**Post-VG-1b API:** `Switch2ProInputs` with family-native inputs only, `inputs()`, `set_inputs`, per-field setters and `edit_inputs` delegating to the same transactional final-state validator on both handles. Battery/charging, caller-specified per-instance identity (#156, #162), protocol clocks/status, topology, calibration and retained host outputs are separate typed views, not editable input fields. No compatibility aliases or universal grip-button model. VG-1b d/e are still landing; this brief assumes they have finished and does not modify their branches. Preserve explicit `commit()`/`service()`, neutralization of input levels only, ordered last accepted edit wins, full rollback and no new dirty work for unchanged edits (preserve already queued work). Controller-owned motion clocks change only on qualifying accepted transitions; no inferred cadence or queued intermediate input edges.

Keep identity stable within each instance and caller-restorable where the target supports it; defaults must be unique for concurrent instances. USB PID/version, firmware revision, serial and SDL GUID are not interchangeable. Expose only fields the target represents; document evdev-only identity, not retail enumeration. Do not publish real identifiers or calibration material.

## Ordered steps (separate implementation PRs, each to main)

**20a. **20b. Reduced playable uinput and conventional FF.** Present source-declared main evdev gamepad with exact key and axis set (including separate GR/GL/C and KEY_RECORD), signed stick axes, hat, digital triggers, and conventional two-magnitude FF if source/provider contract is reviewed. ## Host setup and audit impact

Existing signed-off #258 defaults apply to the reduced target: existing trusted creator access to /dev/uinput, consumer event-node permissions and optional write for FF; ordinary caller, no broad input group or automatic new udev policy. Check kernel input definitions, actual ACL/seat and exact device owner; report module/permission failures rather than running everything privileged. If existing lab isolation rules need expansion for this family, list that as a dev change and audit it before enabling.

**New dev changes (not preauthorized by the Alpha 2 sign-off):** USB/IP/VHCI module availability, reserved attach ports and per-profile worker/broker scope; compiled composite USB topology and ownership journals; libusb /dev/bus/usb node grants, per-device hidraw/event/LED/IMU access, interface claims, kernel driver detach/rebind and collision with another consumer; sandbox access; reversible disconnect, crash and partial attach cleanup. No global USB/driver blacklists, automatic module loads, persistent permission grants or new broker wire rights by default. Use explicit opt-in and the smallest per-device/seat-scoped grants.

Secondary dummy_hcd additionally needs a separate review of module and ConfigFS/gadget mounting, reserved UDC, USB vendor bulk function availability, f_hid metadata/negative reply gap and privileged broker/recovery. Audit each path independently in a #258-style amendment to `docs/ALPHA_2_HOST_AUDIT.md`: mechanism, who/function, required privilege, scope/persistence, security/other-device impact, cleanup/reversibility, safe default and evidence. Obtain renewed Anders sign-off before enabling each. Test close/crash cleanup and verify no unrelated ports, devices or ACLs are touched. Real Bluetooth remains deferred and no BlueZ setup is needed.
