## Goal and decided context

Add a separate curated Elite Series 2 package, not an option that widens the standard Xbox Series button enum. The ordinary root and curated API use `create_xbox_elite_series_2(CreationOptions, XboxEliteSeries2Options)` (C7), an Elite-native handle and `XboxEliteSeries2Inputs`. Steps d/e of VG-1b are still landing; this brief assumes VG-1b has finished and uses its target shape, not the current Xbox Series mixed-state API. `inputs()` reads accepted inputs; `set_inputs`, per-field setters, `edit_inputs` and neutralization delegate to one realization-aware transactional final-state validator. Rejected edits preserve accepted levels, clocks, dirty work and queued reports; accepted no-ops do not add dirty work or consume pending work. Explicit commit/service remain; callers commit between edges. No compatibility aliases, generic controller state, runtime profile engine or implicit fallback. Battery, identity, clocks, topology, retained host output, and any evidenced profile/configuration metadata are separate typed views, not caller input fields.

Caller-specified identity at creation with unique per-instance defaults (#156, #162); disclose transport-specific representability. Use separately reviewed model identities, non-identifying defaults, and the existing association/lifecycle mechanism. An evdev input ID is neither USB bcdDevice nor a Bluetooth HID firmware revision; customization does not turn uinput into a USB device. Never invent identifying data or copy a Series identity variant onto Elite.

- **First — `linux.uinput`:** playable compatibility with the stock Elite xpad post-driver surface. Ordinary Xbox inputs plus four independent *consumer-visible, unmapped* paddle levels; no Share. Treat this as the unremapped presentation only, not an onboard remapping simulator. An active/custom profile can suppress independent delivery in xpad and SDL; the library cannot silently translate a paddle to A/B/X/Y. A caller that wants mapped ordinary button levels supplies those levels itself. Reject any unsupported profile/configuration request before creating or editing the target; do not pretend the profile was set. Do not claim all retail profiles expose four keys.
- **Second — `linux.uhid.bluetooth`:** later, evidence-gated local BUS_BLUETOOTH presentation for a specific Elite descriptor/version, with the greatest supported native input and output coverage. Match stock hid-microsoft first; treat optional xpadneo and SDL raw selection as separate consumers, never stock equivalents. A proposed synthetic descriptor experiment, if separately approved, is WIP compatibility only and is not a prerequisite for shipping uinput. No real radio, pairing, reconnect-at-radio or BlueZ implementation (#164).
- **Out of scope:** Series 1 (#359), Series 3 (#358), standard Series, generic Xbox One, mechanical trigger-stop setting and configuration app simulation without host-visible evidence, as well as any wired USB/GIP or Xbox Wireless receiver implementation (#168 and #165). GIP is never faked: USB-bus UHID and USB-HID-only dummy_hcd are inapplicable to its wired GIP interface. If #168 establishes a real USB-level implementation, follow brief 17's precedent: USB/IP production target; dummy_hcd secondary experimental path only as needed, subject to its ability to represent actual GIP rather than f_hid impersonation. Both need separate #258-style amendments and renewed sign-off. Receiver associations/topology remain with #165. No adapter, audio or firmware work here.
