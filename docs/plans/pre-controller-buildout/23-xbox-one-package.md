## Goal and decided context

Recommend a separate curated Xbox One family, not a Share-disabled Xbox Series variant. The source-backed USB identity matrix, absence of native Share, distinct Bluetooth IDs and firmware-dependent report shapes make this a native contract difference. Within Xbox One, use explicit standard USB identity presets and, only when independently supported, One S model 1708 Bluetooth profiles. Exclude Elite, Adaptive and third-party controllers. Both registry records have null parents; the recommendation is an architectural inference, not an owner decision or an implementation.

- **Playable first — `linux.uinput`:** Xbox One xpad-shaped gamepad, one logical controller and one event device. Expose the eleven native digital keys (A/B/X/Y, bumpers, View/Menu/Guide, two stick clicks), two signed sticks, two analog triggers and D-pad hat. No native Share, extra paddles or profile key. Implement conventional two-main-motor FF with retained typed output; explicitly disclose unsupported FF features, impulse-motor independence and missing native transport behavior. The USB bus label is evdev metadata, not a USB device.
- **Later faithful candidate — `linux.uhid.bluetooth`:** local Bluetooth-bus HID only for a separately evidenced One S revision/report profile. Do not enable Bluetooth for original/2015 USB presets merely because the family name is the same. No Series descriptor reuse by assumption. Real Bluetooth discovery/pairing, radio latency and bond management stay with #164. No generic descriptor injection or implicit fallback.
- **Wired protocol:** USB GIP and receiver feasibility stay with #168. Never fake GIP or advertise USB-bus UHID/USB HID as Xbox One wired transport. If actual GIP feasibility is established in that track, a separate future brief can target USB/IP for production (brief 17 precedent), with `dummy_hcd` only a secondary experimental path if technically viable. Each needs its own #258-style audit amendment and renewed sign-off. Neither is an implementation step here; neither changes the existing `dummy_hcd` restrictions.

The post-VG-1b target is `create_xbox_one(CreationOptions, XboxOneOptions)` on both curated and ordinary root, returning an Xbox One handle with `XboxOneInputs`, `set_inputs`, per-field setters, fallible `edit_inputs`, and `inputs()`. All mutation paths, including neutralize, delegate to one transactional, realization-aware final-state validator: last accepted edit wins, rejection leaves state and dirty/pending work unchanged, and identical accepted snapshots add no dirty work. Keep explicit commit/service semantics; the caller commits between meaningful edges. Identity/revision, battery where representable, controller-owned clocks, topology and retained host outputs are separate typed views, not input fields. No generic input masks, fabricated sensors or compatibility aliases. VG-1b steps d/e are still landing; this brief assumes they are done, not the current interim mixed-state API.

C7 identity is caller-specified at creation with per-instance defaults (#156, #162). Separate revision/transport compatibility from identity values. Specify representable identity fields and stable instance-lifetime defaults; validate unsupported fields or profile/transport combinations before provider open, keep simultaneous devices isolated, and never invent a retail serial or firmware value. Custom identity is allowed but may alter consumer classification; do not promise that arbitrary identity overrides retain stock SDL mappings. A nominal evdev VID/PID is not a unique instance identifier. Compatibility shims, if justified by evidence, must be explicit and toggleable at creation with tested on/off behavior.

For uinput expected evdev keys are BTN_A/B/X/Y, BTN_TL/TR, BTN_SELECT/START/MODE and BTN_THUMBL/THUMBR, no KEY_RECORD. ABS_X/Y/RX/RY are signed -32768 to 32767, ABS_Z/RZ 0 to 1023, ABS_HAT0X/Y -1 to 1 (positive right/down); center sticks/hat and release buttons/triggers at neutral. ## Host setup and audit impact

The signed-off #258 Alpha 2 audit covers existing release defaults, not blanket approval for newly exposed host surfaces. For 23c/23e use creator access to /dev/uinput and consumer distro/seat ACLs on event nodes (including FF write access where needed), exact node attribution, no automatic broad grants. For 23g/23h local Bluetooth-bus UHID requires creator access to /dev/uhid, stock kernel HID driver availability, consumer event/hidraw ACLs and isolated driver ownership; no radio or BlueZ dependency. Existing Series dev-only lab behavior is precedent, not automatic authorization for new IDs.

**Potential new surfaces (dev changes, not authorized by this brief):** expanding Xbox lab rules or active-seat visibility to One IDs, hidraw permission overrides, targeted xpadneo/stock-driver binding overrides, raw-HID compatibility or new privileged broker/helper operations. If needed, amend `docs/ALPHA_2_HOST_AUDIT.md` in #258 style for each mechanism: who, privilege, scope/persistence, other-device/security impact, rollback/cleanup, release default and evidence; obtain renewed owner sign-off before enabling. Prefer isolated device-scoped temporary dev changes; no global hidraw/input grants, root defaults, automated installs or kernel module/policy changes. Any future USB/IP GIP feasibility must separately audit attach/worker/service, USB node permissions and driver/interface ownership; a separate experimental dummy_hcd amendment covers module/configfs/gadget permissions and cleanup. Neither enables fake GIP.

## Snapshot, migration and acceptance consumers

This planning PR adds no code, API snapshot, acceptance manifest, migration entry, research pin or host policy changes. Pinned SDL HIDAPI and kernel hid-microsoft are separately tested for admitted Bluetooth profiles, with hid-generic and xpadneo as distinct optional configurations. SDL may classify both generations as Xbox One family; verify controls and exact backend rather than assuming a UI label proves identity. Steam Input is a manual separate consumer (including Guide caveat); no passing result from permissions or Series observations alone. Physical USB/Bluetooth reference and motor behavior need independent permitted evidence. Synthetic tests, virtual-live and retail physical observations are separate.
