## Goal and decided context

Add a curated original Elite package and ordinary-root handle, provisionally `create_xbox_elite_series_1(CreationOptions, XboxEliteSeries1Options)`, with corresponding input-only `XboxEliteSeries1Inputs`. A separate narrow family is recommended (owner question 1); share small Xbox evdev primitives and session machinery with Xbox Series (brief 15) and the standard Xbox One (#355, parallel brief 23), not a widened common public input type. Brief 23 was not on the inspected main; coordinate extraction and naming before code lands, without making this brief depend on its text or duplicating another implementation PR. Elite 2 (#356) independently establishes its own surface. Keep this post-Alpha 2.

- **First realization — `linux.uinput`:** playable, xpad-shaped, original Elite default wired consumer identity (Microsoft 0x045e / 0x02e3), full source-backed buttons and axes, four independent host-visible paddle levels, conventional two-motor FF when supported. No Share or Elite 2 profile axis. This presents post-driver events, not the original USB endpoint or wireless device.
- **Faithful realization:** none established. Original Elite is scoped to wired USB GIP and proprietary Xbox Wireless; no Bluetooth HID target (the corpus grades the negative transport finding as inferred, not measured). Neither `linux.uhid.bluetooth` nor USB-bus UHID is a substitute for GIP. Actual Bluetooth remains #164; do not create a target simply because another Xbox model uses it.
- **GIP is never faked** (#168). USB/IP is the production target for a *future evidenced and feasible USB-level realization*, following brief 17's owner decision; `dummy_hcd` is secondary, experimental and subject to its known interface limitations. Neither is admitted to this package by this brief. A real USB GIP path and Xbox Wireless receiver support require independent research, protocol feasibility, authorization and per-path permission reviews; no generic HID spoofing, fabricated handshake, or implicit fallback.
- Paddles model **independent post-xpad key levels**, not a retail remapping engine. Current-vs-factory mapping guards suppress independent paddle reports in both reviewed kernel and SDL GIP decoder paths. Do not infer independent physical events from advertised keys. Do not model profiles, Shift, firmware mapping tables, configuration commands, headset/audio or impulse motors as ordinary inputs. The issue's expected two profiles are not a measured consumer-visible control; count/switch semantics remain a device question.

C7 identity is caller-specified at creation with per-instance defaults (#156, #162). Distinguish stable family identity/type from caller-selected representable evdev name, bus/vendor/product/version or other supported creation identity fields. Keep the family/realization explicit even when identity overrides alter consumer recognition; reject unrepresentable identity requests, not silent truncation/fallback. Verify which fields the provider actually publishes; no native USB serial or descriptor fidelity from evdev. Simultaneous default instances must remain independently attributable.

The brief **assumes VG-1b steps d and e have landed** (not the interim API). Use family-typed input-only `XboxEliteSeries1Inputs`, `set_inputs`, native per-field setters and fallible `edit_inputs` across curated and root, plus `inputs()` as accepted read view and `neutralize()`. One transactional final-state validator installs accepted changes; rejected edits preserve desired state, dirty flag, pending work and separate views. Accepted no-ops add no new dirty work; existing pending work survives. Battery/status, identity, clocks/counters, topology and typed host outputs stay separate; unsupported metadata operations are refused rather than synthesized. Preserve explicit `commit()`/`service()` and retry/lifecycle contracts; no edge queue or consumer atomicity guarantee, caller commits between edges. No generic canonical input map, profiles/plugins, or compatibility aliases.

The pinned xpad surface is 15 EV_KEY controls (four face, two menu, two stick clicks, two bumpers, Guide, and four grip paddles) and eight EV_ABS axes. Use stock stick codes ABS_X/Y/RX/RY, signed -32768..32767, fuzz 16 and flat 128; ABS_Z/RZ triggers 0..1023; ABS_HAT0X/Y in -1..1. Standard face/menu/stick/shoulder/Guide codes derive from the cited xpad arrays; no Share KEY_RECORD or Elite 2 profile axis. Grip keys are BTN_GRIPR, BTN_GRIPR2, BTN_GRIPL and BTN_GRIPL2; do not alias them to BTN_TRIGGER_HAPPY5–8. Conditional FF_RUMBLE supplies only two conventional magnitudes. Use source-backed code names and mapping; compare complete runtime capability/axis lists, not just counts. The existing Series provider has zero axis fuzz (brief 15); if still true, record that mismatch explicitly, do not promise retail fuzz/filtering. Independently verify name/version, neutral, axis polarity, all ancillary capabilities and FF effect lifecycle before declaring an exact match. SDL 3.2.0's built-in original-Elite mapping contains no explicit paddles, and its automatic Linux path checks legacy codes. The newer pinned Linux backend recognizes grip keys directly and retains the legacy fallback. SDL HIDAPI's original Elite parser suppresses remapped independent paddles; it is not an evdev parser and cannot establish a uinput HIDAPI path.

## Ordered steps (separate implementation PRs, each to main)

**24a.
