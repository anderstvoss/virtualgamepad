## Goal and decided context

Hold a preliminary slot for Elite Series 3 until actual public evidence identifies its controls, transports, revision differences and identity. Do not ship a speculative constructor, controller type, descriptor, PID, layout, profile, or support claim. Even paddles, sticks, profile switches and compatibility with Series 2 are unknown for this target.

For Nano, the #357 marketing summary suggests a compact D-pad/face/top-button device, programmable Action Button, controller-side remapping, internal rechargeable battery, Bluetooth and Xbox Wireless. These are research leads, not a verified native control inventory. USB-C may be charge-only; enumeration or charging is not proof of playable USB data. No thumbsticks, trigger axes, Share, rumble or other unstated control may be inferred from Series branding; confirm absence or presence before deciding the type. Model the Action Button as a native input only if independently reportable, otherwise document the observed remapped/control-side behavior. A remapped control is not both a new independent host button and its reassigned function unless evidence shows both. Do not synthesize stick/trigger events or duplicate logical presses. A caller-requested unsupported configuration or meaningful non-neutral input must fail explicitly. No off-device profile editor, remapping vendor command or persistent configuration work without source evidence and separate scope; no firmware examination.

Prefer separate native Nano shape, with Elite 3 package versus an Elite-owned variant decided only after research. Share narrow, evidenced Xbox primitives (axis conversion where identical, evdev/FF mapping plumbing, identity/lifecycle, transactional validation, protocol framing where proven identical) rather than inheriting Series/One/Elite controls, defaults, packet layouts, descriptors or IDs. Keep the compiled curated architecture, no runtime profiles, implicit realization fallback, generic state or provider-owned semantics.

- **C7 and post-VG-1b:** after evidence and family decision, use `create_<family>(CreationOptions, <Family>Options)` in curated and ordinary root, e.g. `create_xbox_nano(CreationOptions, XboxNanoOptions)` if a separate family is chosen. If Elite 3 qualifies as a variant, use the chosen Elite constructor's explicit creation variant, not an alias or silent widening of another family's inputs. The family-typed `<Family>Inputs`, `inputs()`, `set_inputs`, field setters, `edit_inputs` and neutralize delegate to one transactional final-state validator (same refusal, rollback, dirty/no-op and qualifying clock rules). Battery, identity, clocks, topology, remap/profile metadata (if independently evidenced) and host output are separate typed views. Keep explicit commit/service and no intermediate-edge guarantee: callers commit between important edges. This brief assumes VG-1b is complete; steps d/e are still landing, so no dependence on its interim mixed-state shape or compatibility aliases.
- Identity (#156/#162): caller specified at creation, unique per-instance defaults; only evidenced meaningful fields, with stable lifetime, collision behavior and explicit per-realization representation limits. Never manufacture retail identity or copy private device identifiers.
- **Playable** `linux.uinput`: likely shared Xbox provider infrastructure, but only target-specific proven controls and a documented host-facing shape; each deviation has a reason and regression. Toggle any compatibility shim at creation, label it as such, and never change native type solely to satisfy a host mapping.
- **Faithful local HID** `linux.uhid.bluetooth`: leading candidate for Nano if HID report/binding evidence arrives; possible Elite 3 only if Bluetooth is established. BUS_BLUETOOTH here is local kernel metadata, not over-the-air discovery, pairing or reconnect (#164).
- **Faithful USB:** if evidence shows a USB data protocol, select actual HID vs GIP from evidence. For USB-level paths USB/IP is the production target and `dummy_hcd` secondary experimental, following brief 17's owner decision; each requires independent #258-style audit amendment and owner sign-off. USB-bus UHID is not a GIP device. No USB pad at all if USB-C only charges. Heavy-permission features have separate realizations, not hidden escalation or fallback.
- **Xbox Wireless:** only via the #165/#168 receiver/GIP design, verified association and client lifecycle, never faked through evdev or UHID. Real Bluetooth remains deferred.

## Host setup and audit impact
